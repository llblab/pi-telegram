Corrected locally: the follower probes its live registration before re-registering, a slow forwarded tap is released after about 1.5 s, the retryable-forward toast no longer claims foreign ownership, follower callback answers ignore Telegram's expired-query rejection, and the Thread capability rides the heartbeat acknowledgement instead of per-follower `getMe` probes. Responsiveness is the priority: no multi-second caching of capability state, and detection of a dead follower must not slow down.

Measured on a copy of the live state (2026-11-03): reading and parsing `state.json` takes about 0.7 ms, writing and renaming it about 0.3 ms, appending a log line about 0.01 ms, so state transactions hold for a few milliseconds and contended 25 ms lock waits cannot explain multi-second stalls. The leader processes also ran at 60–70% CPU, so busy JavaScript in the same process (the host application's own turn work or rendering) is the leading suspect, which extension code cannot unblock; the stall record's `cpuMs` and `blocked` fields separate these causes.

Finding that changes the earlier hypothesis: heartbeats already use their own connection per request and the leader's heartbeat handler is synchronous, so slow follower API calls cannot queue them. The leader logged `write EPIPE` right after each follower timeout, meaning it answered after the follower's eight-second deadline: its event loop was stalled for several seconds, cause unknown. Leader-lane separation is therefore not a fix.
