# Confirmed quit foundation

## Authority and boundary

The operator approved and live-accepted a confirmed, current-Thread-only Telegram quit design. Baseline: `v0.51.5`, commit `8a72158990d341ae4e11b45f47beb5921e67cf64`. The candidate checkout is not the installed Pi package.

The follower-only production composition is implemented, offline-validated, and live-accepted with disposable candidate leader and follower peers. `/quit` is registered in the candidate, renders an exact confirmation, waits for durable command and callback completion, invokes the existing authenticated follower close/delete path, and calls the captured public Pi shutdown only after confirmed deletion plus a fresh disconnected/idle check. No new protocol capability or persistence schema was added. Shared transport-owner exit remains unsupported; ordinary terminal quit behavior is unchanged.

## Current v1 scope: confirmed quit and delete

The operator has explicitly chosen **quit the current Pi and delete its own Telegram Thread/messages**, primarily to clean up Telegram. This supersedes the earlier v1 requirement to support both cleanup choices:

- Confirmation must explicitly disclose deletion of that exact Thread/messages first, then Pi exit only if the same Pi is still idle and disconnected. The operator approved partial success: if Pi becomes busy during cleanup, keep it running with Telegram disconnected, never interrupt it and never schedule a later quit. No keep-Thread option in v1. Explicit deletion applies even when automatic cleanup is OFF; ordinary terminal quit continues to honor its existing setting.
- A future v1 snapshot adapter supplies explicit deletion consent (`automaticCleanup: true`) rather than copying the automatic-cleanup preference. Preference flips alone do not invalidate this fixed action; identity, idle, admission, ownership and other evidence fences still do. The generic Q1 foundation and its older two-choice regressions are retained, not exposed as v1 options.
- Idle follower/last-instance exit remains the target. Busy/unknown before cleanup refuses the action; busy/unknown at the post-cleanup check means no Pi exit. Existing accepted work is not discarded. A shared transport owner with dependents still refuses. Other Pis and their Threads remain untouched.
- Confirmed deletion may reuse the existing authenticated follower disconnect, cleanup intent, reconciler and persisted exact-target deletion observation. A successful disconnect ACK is not deletion proof: a protected replacement can retain the Thread. Use the exact optional deletion outcome described in [the bus contract](./multi-instance-bus.md#protocol-identity-and-compatibility), with missing/unconfirmed outcomes refusing Pi exit. The disconnect operation alone does not stop Pi. A failed or ambiguous deletion must retain recovery evidence and must not be reported as confirmed deletion.
- **Keep-Thread consent propagation and preservation coordination are out of scope for v1.** Do not add that protocol/state machinery. Before proposing any new retained closing state, test whether existing deletion intent/facts suffice for the delete-only lifecycle.

Successful/ACK-lost deletion leaves an exact deletion observation that survives reopening the store; failed deletion retains the intent and registration. Another registered follower/Thread remains untouched. Tests use authenticated local IPC, real temporary stores and fake Telegram effects, not live deletion or Pi exits.

That scope checkpoint reproduced a real boundary: cached ownership could delegate an old deleted-target update before the unbound-Thread deletion check. The locally implemented guard below now addresses that case without changing general handoff ownership. The operator explicitly accepted successful Thread deletion/disconnection even if Pi becomes busy before exit: leave Pi running, without an eventual automatic quit. This removes the requirement that cleanup success and Pi exit be inseparable; it does not authorize dropping accepted work or starting cleanup before initial idle/admission authority is established.

That decision, source-side closing, follower disconnection, confirmation UI and production lifecycle composition are implemented, and disposable real-process/real-Thread acceptance is complete. Publication, merge, release, and permanent installation remain separate actions; leader-owner quit remains deferred.

## Slice Q1: fenced shutdown handoff

Outcome: a one-use, exact-instance confirmation closes a local admission gate, requires positive quiescence evidence, acknowledges shutdown, waits for the exact durable confirmation-update completion, revalidates, captures cleanup consent, and invokes one injected graceful-shutdown port. No model turn, shell, terminal injection, process kill, Thread deletion, or configuration write belongs to this domain.

Scope includes confirmation identity and expiry, exact scope equality, local admission counting, state transitions and failure handling, immutable cleanup consent, and integration tests with the existing update-completion owner adapter. The downstream UI, leader-mediated admission coordination, real lifecycle wiring, capability negotiation, election, and live failover evidence are excluded.

### Identity and evidence

`TelegramQuitScope` binds the profile/token generation key (not the token), bot, paired owner, numeric chat/Thread target, process instance/birth, session and generation, and exact transport registration/epoch generation. Human-readable Thread names never authorize an operation. A confirmation additionally binds its delivered message ID, paired actor, random one-use token, and a 60-second expiry. Unknown or invalid scope is refused.

A caller supplies a freshly refreshed snapshot and a synchronous final read. Quiescence must be explicitly `clear` for agent/tools, Pi pending messages, all Telegram queue items (including skipped items), dispatch/control transitions, compaction, grouped inputs, accepted input/forwarding mutations, and pending output delivery. Missing or unknown evidence is never empty-work proof. The quit confirmation's own exact control receipt is the only allowed exclusion from input-pending evidence.

**Minimal v1 defers transport-owner exit with dependents**: unknown membership/ownership refuses, and shared-owner exit must refuse. Idle follower and last-instance exit remain intended, not end-to-end verified. The foundation's broader evidence contract below does not authorize that deferred case.

Transport evidence includes role, a stable cohort identity key, and positive quit-support/readiness. For a leader with survivors, all participating peers must support the eventual quit-safety contract, with at least one freshly authenticated eligible survivor. Membership, registration, role, or cohort change invalidates confirmation. Refresh timestamps alone must not change the cohort key. Zero survivors is represented explicitly; eventual UI must warn that Telegram goes offline.

### Admission and transition contract

- Each session has its own gate. `enter(scope)` must precede an admission/dispatch effect and its returned release must run only after the admitted operation settles. The gate owns counts, not queued work or journal authority.
- `tryClose(scope)` succeeds only for the exact scope with no admitted operations. It synchronously rejects later admissions until reopened or permanently sealed. Refusal never settles, deletes, or transfers the refused input; its upstream owner must retain custody or publish an explicit closing rejection.
- The future distributed adapter must close both receiving-instance and leader-forwarding admission for the exact target, and project pre-existing accepted inputs into quiescence evidence. A process-local gate alone is **not** cross-process exclusion. No production caller currently uses this gate.
- Valid confirmation is consumed before the first await. Busy, stale, unknown, policy-changed, or unsupported evidence reopens only that attempt's local gate and requires a new confirmation. Concurrent calls and copied callbacks cannot replace the attempt.
- Refresh/acknowledgement ports receive cancellation and an authority assertion. They must assert immediately before any external effect and after awaited work. Expiry, cancellation, and disposal stop waiting even if a port never settles; late results cannot arm shutdown. An already-sent acknowledgement cannot be unsent, so the future UI must say only "Shutting down" and correct a later refusal when it still owns delivery.
- A successful acknowledgement arms exactly one source update. Only the journal owner's **post-completion** callback for that exact update and scope may advance it; a callback observed before arming has no effect. The runtime schedules its final work outside that callback's stack, so worker teardown cannot wait on the callback that requested it.
- Final refresh and synchronous validation occur while the gate is closed. Immediately before invoking shutdown, seal the gate and publish an immutable, exact-scope cleanup consent. There is no await between that decision and the shutdown call. Setting changes before this point refuse; later settings changes apply to subsequent operations, not this teardown.
- The future lifecycle adapter must carry this same consent through all deletion/preservation paths, including follower-to-leader cleanup. `getCleanupConsent(scope)` returns it only for the exact committed scope. It is not a Telegram deletion permit and never bypasses reconciler/admission rules. It expires with this runtime; a successor cannot replay it.
- Once the shutdown port is invoked, it is never retried. A throw has unknown outcome: retain the sealed gate and consent, and report `outcome-unknown`, not success or a safe-to-retry failure. Only real process/lifecycle evidence can prove exit.

### Proposed contract

1. Close ordinary admission for the exact follower registration/Thread, on both receiving and source-owning sides. Capture current scope and check existing accepted work; busy or unknown refuses rather than waiting for ordinary work to drain. Do not stop shared polling or other followers.
2. The source owner handles input arriving after that boundary explicitly as closing traffic, without admitting it to Pi, rerouting it to the leader, or silently transferring it to a successor. Preserve its disposition through notification failure, journal-write uncertainty, and owner replacement. Never retroactively reject earlier uncertain deliveries.
3. Prove both copies of the exact confirmation source settled before the final Pi shutdown decision. Lost/stale/mismatched acknowledgements cannot grant completion or reopen committed admission. Any bounded wait here is only for the operation's own control settlement, not a queued-quit feature.
4. Convey the immutable cleanup choice through a narrowly scoped, authenticated and capability-gated quit operation. The leader must use that exact choice for this teardown, not current settings. No Thread deletion or inactivity publication precedes the required quit/teardown authority; native terminal quit keeps its current path.
5. Unknown commit outcome stays protected and cannot replay shutdown, erase accepted work, or turn a keep choice into deletion. Session/registration replacement, leader epoch changes and unsupported peers fail closed. Any new retained state belongs to an existing authoritative owner, not a parallel registry or debug snapshot; compatibility and recovery must be defined before activation.
